# Почему приложение работает без backend

## Контекст

Это фронтовое тестовое задание. Приложение демонстрирует интеграцию React-интерфейса с WhatsApp через GREEN-API: пользователь сам вводит реквизиты своего инстанса, создаёт чат по номеру телефона, отправляет текстовые сообщения и получает ответы.

Для решения выбрана прямая схема взаимодействия:

```text
React-приложение в браузере → GREEN-API → WhatsApp
```

Собственный backend, proxy или BFF в этой схеме не участвует.

## Почему выбран этот путь

Главная цель задания — показать реализацию клиентского интерфейса и работу с API. Отдельный сервер увеличил бы объём решения за счёт инфраструктуры, передачи и хранения реквизитов, настройки окружений и развёртывания, но не помог бы проверить основные фронтовые навыки.

Прямые запросы из браузера дают несколько преимуществ для тестового проекта:

- приложение запускается одной командой и не требует отдельного сервера;
- проверяющий может использовать собственный инстанс GREEN-API;
- весь основной сценарий реализован на стороне клиента и доступен для изучения;
- реквизиты не передаются и не сохраняются на сервере приложения, потому что такого сервера нет.

Это осознанный компромисс для демонстрационного проекта, а не рекомендуемая архитектура публичного production-приложения.

## Работа с GREEN-API

Для запросов используется универсальный хост `https://api.green-api.com`. URL метода формируется из `idInstance`, имени метода и `apiTokenInstance`:

```text
https://api.green-api.com/waInstance{idInstance}/{method}/{apiTokenInstance}
```

Официальное описание формата запросов: [Выполнение запросов в WhatsApp API](https://green-api.com/docs/request-format/).

### Отправка сообщения

До входа приложение проверяет состояние инстанса методом `GetStateInstance` и продолжает работу только при `authorized`. Номер получателя нормализуется до международного формата без `+`, пробелов и знаков пунктуации, локально проверяется на длину 11–16 цифр, а затем подтверждается методом `CheckWhatsapp`. Для личного чата из него формируется идентификатор вида `79991234567@c.us`, но после проверки используется `chatId`, возвращённый GREEN-API.

Текст отправляется методом [`SendMessage`](https://green-api.com/docs/api/sending/SendMessage/):

```json
{
  "chatId": "79991234567@c.us",
  "message": "Привет!"
}
```

### Получение сообщений

Входящие события читаются периодическими запросами к [`ReceiveNotification`](https://green-api.com/docs/api/receiving/technology-http-api/ReceiveNotification/). GREEN-API возвращает уведомления из общей очереди инстанса по одному, в порядке FIFO. Если очередь пуста, API возвращает `null`.

Цикл обработки одного уведомления выглядит так:

1. Получить уведомление через `ReceiveNotification`.
2. Проверить тип события и извлечь `textMessage` либо `extendedTextMessage` активного чата.
3. Добавить подходящее сообщение в состояние интерфейса.
4. Подтвердить обработку методом [`DeleteNotification`](https://green-api.com/docs/api/receiving/technology-http-api/DeleteNotification/).

Удалять уведомление нужно только после того, как клиент закончил его обработку. Если не удалить уведомление, следующий вызов снова вернёт элемент, находящийся в начале очереди. Уведомления хранятся в очереди 24 часа. Подробнее: [получение уведомлений через HTTP API](https://green-api.com/docs/api/receiving/technology-http-api/).

## Хранение реквизитов

`idInstance` и `apiTokenInstance` хранятся только в памяти React-приложения. Они не записываются в `localStorage`, `sessionStorage` или cookies и сбрасываются после перезагрузки страницы.

Файл `.env.development.local` используется только для удобства локальной разработки. Переменные Vite с префиксом `VITE_` попадают в клиентский код и **не являются способом безопасного хранения секрета**. Файл с реальными реквизитами не должен попадать в Git, а production-сборка не должна содержать тестовые значения.

## Риски и ограничения

### Токен доступен в браузере

GREEN-API передаёт `apiTokenInstance` как часть URL. При прямом запросе токен доступен выполняемому JavaScript-коду, виден владельцу устройства в DevTools и может попасть в диагностические данные или логи сетевой инфраструктуры. HTTPS защищает запрос при передаче, но не скрывает реквизиты внутри самого браузера.

Следствия:

- приложение нельзя считать безопасным способом раздать доступ к одному инстансу множеству недоверенных пользователей;
- реквизиты нельзя логировать или выводить в сообщения об ошибках;
- при подозрении на компрометацию токен необходимо заменить в личном кабинете GREEN-API;
- сторонние скрипты увеличивают риск утечки, поэтому проект не должен подключать их без необходимости.

### Зависимость от CORS

Прямые запросы работают только пока GREEN-API разрешает их с origin, на котором опубликовано приложение. Политика CORS контролируется поставщиком API. Если нужный origin или заголовки перестанут поддерживаться, исправить это только на стороне React-приложения будет невозможно.

### Одна общая очередь уведомлений

Очередь принадлежит инстансу, а не конкретной вкладке или открытому чату. Одновременный запуск приложения в нескольких вкладках или параллельное использование другого HTTP API-клиента приводит к конкуренции потребителей: уведомление обработает тот клиент, который первым его получил и удалил.

Для тестового проекта поддерживается один активный клиент на один инстанс. Получатель уведомлений обязан проверять `chatId` и тип события, но обработать и удалить нужно также неподходящие события, иначе они заблокируют продвижение очереди.

### Polling и ограничения API

Получение ответов реализуется polling-запросами. Слишком частый polling создаёт лишнюю нагрузку и может привести к ограничениям API, слишком редкий — увеличивает задержку появления сообщений. Polling должен останавливаться при выходе пользователя, размонтировании интерфейса и устойчивой ошибке авторизации или доступа.

Временные сетевые ошибки требуют повторной попытки с паузой. Ошибки авторизации повторять бесконечно нельзя: пользователь должен получить понятное сообщение и возможность исправить реквизиты.

### История ограничена текущей сессией

Сообщения интерфейса находятся в памяти приложения и исчезают после перезагрузки страницы. Очередь уведомлений не является полной историей переписки: она содержит ещё не обработанные события и хранит их ограниченное время.

Загрузка полной истории через дополнительные методы GREEN-API не входит в минимальный сценарий задания. Под «историей сообщений» в интерфейсе понимается переписка, полученная и отправленная в течение текущей сессии.

### Ограниченная поддержка событий

Инстанс может получать не только входящие текстовые сообщения, но и статусы доставки, исходящие события, медиа и системные уведомления. Интерфейс отображает обычный `textMessage` и текст из `extendedTextMessage`, включая сообщения со ссылкой. Остальные события корректно распознаются, пропускаются и подтверждаются, чтобы очередь продолжала обрабатываться.

### Адаптивный интерфейс

На desktop при ширине от `768px` список чатов и переписка видны одновременно. На mobile от `320px` до `767px` это два представления с явной кнопкой возврата. Переключение представлений не перезапускает polling и не удаляет состояние текущей сессии.

## Меры снижения рисков

Для выбранной архитектуры применяются следующие ограничения:

- хранить реквизиты только в памяти приложения;
- не включать токен в логи, пользовательские ошибки и аналитику;
- не сохранять реальные реквизиты в репозитории;
- запускать только один получатель уведомлений на инстанс;
- удалять уведомление только после завершения его обработки;
- останавливать polling, когда он больше не нужен;
- явно сообщать пользователю об ошибках авторизации, сети и API;
- ограничить приложение заявленным сценарием работы с текстовыми сообщениями.

## Когда потребуется backend

Промежуточный backend или BFF потребуется, если приложение станет публичным или production-ориентированным. Сервер позволит не передавать токен GREEN-API в браузер, централизованно читать очередь один раз, распределять сообщения между пользователями, контролировать доступ, выполнять повторные попытки и вести безопасный аудит.

Для данного тестового задания эти задачи находятся вне заявленного объёма. Поэтому прямой доступ из браузера выбран как наиболее простой способ продемонстрировать требуемую фронтовую интеграцию, а его ограничения зафиксированы в этом документе.
