# Техническое задание: WhatsApp-чат через GREEN-API

Статус документа: проект для согласования  
Версия: 1.0  
Состав релиза: только MVP

## 1. Контекст

Необходимо разработать клиентское React-приложение для отправки и получения текстовых сообщений WhatsApp через GREEN-API.

Исходное тестовое задание допускает использование WhatsApp вместо MAX. В проекте используется WhatsApp API, а внешний вид интерфейса создаётся по мотивам веб-версии MAX. API для MAX и WABA не используются.

Приложение является фронтовым тестовым заданием и обращается к GREEN-API напрямую из браузера. Собственный backend, proxy или BFF отсутствует. Обоснование и риски этого решения описаны в документе [«Почему приложение работает без backend»](frontend-only-architecture.md).

## 2. Цель MVP

Пользователь с собственным авторизованным инстансом GREEN-API должен иметь возможность:

1. Ввести реквизиты инстанса и пройти их проверку.
2. Создать личный чат по номеру телефона WhatsApp.
3. Отправлять в выбранный чат текстовые сообщения.
4. Получать ответы и видеть переписку в текущей сессии.
5. Использовать приложение на desktop и мобильном устройстве.

MVP считается завершённым, когда основной сценарий выполняется с реальным инстансом GREEN-API, а перечисленные в разделе 15 критерии приёмки подтверждены.

## 3. Термины

- **Инстанс** — подключённый к GREEN-API аккаунт WhatsApp.
- **Реквизиты** — пара `idInstance` и `apiTokenInstance`.
- **Активный чат** — единственный выбранный в текущий момент личный чат.
- **Уведомление** — событие из входящей FIFO-очереди GREEN-API.
- **Сессия** — время работы приложения до перезагрузки вкладки.
- **Polling** — последовательное получение уведомлений методом `ReceiveNotification`.

## 4. Предварительные условия

Перед началом работы пользователь должен:

1. Создать инстанс в личном кабинете GREEN-API.
2. Подключить к нему аккаунт WhatsApp.
3. Убедиться, что инстанс находится в состоянии `authorized`.
4. Включить получение уведомлений о входящих сообщениях (`incomingWebhook`).
5. Оставить `webhookUrl` пустым для работы через HTTP API.

Приложение не создаёт и не настраивает инстанс автоматически.

## 5. Границы MVP

### 5.1. Входит в MVP

- проверка реквизитов GREEN-API;
- проверка наличия WhatsApp у введённого номера;
- один активный личный чат;
- замена текущего чата новым;
- отправка текстовых сообщений;
- получение входящих текстовых сообщений;
- локальная история текущей сессии;
- обработка загрузки и ошибок;
- адаптивный desktop- и mobile-интерфейс;
- автоматические тесты критической логики.

### 5.2. Не входит в MVP

- несколько одновременно сохранённых чатов;
- восстановление переписки после перезагрузки;
- загрузка истории методом `GetChatHistory`;
- групповые чаты;
- изображения, видео, аудио, документы, контакты и геолокация;
- цитирование, редактирование и удаление сообщений;
- статусы доставки и прочтения;
- список контактов и поиск;
- push-уведомления;
- регистрация пользователей приложения;
- собственный backend и серверное хранение данных;
- WABA и шаблонные сообщения;
- автоматическое создание или авторизация инстанса GREEN-API.

## 6. Архитектурные решения

### 6.1. Общая схема

```text
React UI → типизированный REST-клиент → GREEN-API → WhatsApp
```

Для интеграции используется собственный небольшой клиент на базе `fetch`, а не SDK. Это сохраняет минимальный набор зависимостей, делает сетевой обмен прозрачным и позволяет явно управлять отменой polling-запросов.

### 6.2. API-хост

Для MVP используется универсальный хост:

```text
https://api.green-api.com
```

Общий формат URL:

```text
https://api.green-api.com/waInstance{idInstance}/{method}/{apiTokenInstance}
```

Если конкретный инстанс требует отдельного `apiUrl`, такая конфигурация считается ограничением текущего MVP и должна быть отдельно добавлена в требования.

### 6.3. Клиентское состояние

Состояние приложения разделяется на независимые области:

- реквизиты инстанса;
- статус проверки инстанса;
- активный чат;
- сообщения активного чата;
- черновик сообщения;
- состояния сетевых операций и ошибки;
- состояние цикла получения уведомлений.

REST-клиент GREEN-API не зависит от React. Компоненты не формируют URL методов и не разбирают сырые ответы API самостоятельно.

## 7. Пользовательские сценарии

### 7.1. Вход

1. Пользователь открывает приложение.
2. Приложение показывает поля `idInstance` и `apiTokenInstance`.
3. Пользователь заполняет оба поля и нажимает «Войти».
4. Приложение вызывает `GetStateInstance`.
5. При состоянии `authorized` реквизиты сохраняются в памяти, открывается экран чата.
6. При другом состоянии или ошибке пользователь остаётся на форме и получает понятное сообщение.

Во время проверки кнопка входа заблокирована, повторная отправка формы не выполняется.

### 7.2. Создание чата

1. Пользователь нажимает «Новый чат».
2. Приложение предлагает ввести номер в международном формате.
3. Из номера удаляются пробелы, `+`, скобки и дефисы.
4. Если после нормализации значение содержит не только цифры или имеет длину вне диапазона 11–16 цифр, показывается локальная ошибка.
5. Приложение формирует `chatId` вида `{номер}@c.us` и вызывает `CheckWhatsapp`.
6. При `existsWhatsapp: true` создаётся чат с `chatId`, возвращённым API.
7. При `existsWhatsapp: false` форма остаётся открытой и показывает ошибку.

Новый чат заменяет текущий только после успешной проверки. Сообщения предыдущего чата удаляются из памяти без возможности восстановления.

### 7.3. Отправка сообщения

1. Пользователь вводит текст.
2. Пустой текст или строка только из пробельных символов не отправляется.
3. Пользователь отправляет форму кнопкой или клавишей Enter.
4. Приложение вызывает `SendMessage` для активного `chatId`.
5. До завершения запроса повторная отправка заблокирована.
6. После успешного ответа сообщение добавляется в локальную историю, а поле ввода очищается.
7. При ошибке сообщение не добавляется, введённый текст сохраняется и доступна повторная отправка.

Перенос строки и многострочный редактор не входят в MVP.

### 7.4. Получение сообщения

1. После успешного создания чата приложение запускает цикл `ReceiveNotification`.
2. Полученное уведомление классифицируется по типу и `chatId`.
3. Поддерживаемое текстовое сообщение активного чата добавляется в историю.
4. Неподдерживаемое событие или сообщение другого чата не отображается.
5. После завершения обработки вызывается `DeleteNotification`.
6. Затем начинается получение следующего уведомления.

Одновременно разрешён только один цикл получения уведомлений на вкладку. При замене чата, возврате к форме входа, размонтировании приложения или перезагрузке вкладки текущий запрос отменяется.

### 7.5. Замена чата

1. Пользователь открывает форму нового чата.
2. До успешной проверки нового номера текущий чат продолжает существовать.
3. После успешного `CheckWhatsapp` старый polling останавливается.
4. История и набор идентификаторов старого чата очищаются.
5. Новый чат становится активным и запускает собственный polling.

## 8. Требования к GREEN-API

### API-01. Проверка инстанса

- Метод: [`GetStateInstance`](https://green-api.com/docs/api/account/GetStateInstance/).
- HTTP-метод: `GET`.
- Вход считается успешным только при `stateInstance: "authorized"`.
- Состояния `notAuthorized`, `blocked`, `sleepMode`, `starting`, `yellowCard` и `suspended` отображаются как отдельные пользовательские состояния либо как понятная общая ошибка с фактическим значением статуса.
- Ошибка доступа не должна раскрывать `apiTokenInstance`.

### API-02. Проверка номера

- Метод: [`CheckWhatsapp`](https://green-api.com/docs/api/service/CheckWhatsapp/).
- HTTP-метод: `POST`.
- Используется актуальное поле `chatId`; устаревшее поле `phoneNumber` не используется.
- Тело запроса содержит `chatId: "{нормализованный номер}@c.us"`.
- При успешной проверке приложение использует `chatId` из ответа API, включая возможный идентификатор с суффиксом `@lid`.

### API-03. Отправка текста

- Метод: [`SendMessage`](https://green-api.com/docs/api/sending/SendMessage/).
- HTTP-метод: `POST`.
- Тело запроса содержит только `chatId` и `message`.
- Идентификатор `idMessage` из ответа используется как идентификатор исходящего сообщения.
- Клиентская валидация ограничивает длину текста 20 000 символами.

### API-04. Получение уведомления

- Метод: [`ReceiveNotification`](https://green-api.com/docs/api/receiving/technology-http-api/ReceiveNotification/).
- HTTP-метод: `GET`.
- Для long polling используется `receiveTimeout=5` секунд.
- Ответ `null` означает, что очередь пуста, и не считается ошибкой.
- Поддерживаемые входящие события:
  - `typeWebhook: "incomingMessageReceived"`;
  - `messageData.typeMessage: "textMessage"`;
  - текст берётся из `messageData.textMessageData.textMessage`.
  - `messageData.typeMessage: "extendedTextMessage"`;
  - текст берётся из `messageData.extendedTextMessageData.text`.
- Формат `extendedTextMessage` поддерживается как обычный текст со ссылкой. Метаданные превью и рекламы не отображаются.

### API-05. Подтверждение уведомления

- Метод: [`DeleteNotification`](https://green-api.com/docs/api/receiving/technology-http-api/DeleteNotification/).
- HTTP-метод: `DELETE`.
- В URL передаётся `receiptId`, полученный от `ReceiveNotification`.
- Уведомление удаляется только после классификации и завершения обработки.
- Если удаление не удалось, получение следующего элемента очереди не запускается до повторной попытки удаления или остановки polling.

## 9. Правила обработки уведомлений

Очередь уведомлений является общей для всего инстанса и обрабатывается в порядке FIFO.

Клиент должен:

1. Обрабатывать уведомления последовательно, без параллельных вызовов `ReceiveNotification`.
2. Сравнивать `senderData.chatId` с идентификатором активного чата.
3. Отображать только поддерживаемые текстовые сообщения активного чата.
4. Подтверждать также неподдерживаемые и не относящиеся к активному чату события, чтобы они не блокировали очередь.
5. Дедуплицировать сообщения по `idMessage`.
6. Не добавлять сообщение повторно, если оно уже отображено, а предыдущая попытка `DeleteNotification` завершилась ошибкой.

Для MVP поддерживается только одна активная вкладка на один инстанс. Конкурентное чтение очереди несколькими вкладками или другими клиентами не гарантирует полноту отображаемой переписки.

## 10. Обработка ошибок

### 10.1. Категории ошибок

- локальная ошибка валидации;
- неверные реквизиты;
- неподходящее состояние инстанса;
- номер не зарегистрирован в WhatsApp;
- ошибка или таймаут сети;
- ответ GREEN-API с ошибкой;
- ошибка отправки сообщения;
- ошибка получения или удаления уведомления;
- ограничение частоты запросов.

### 10.2. Требования к поведению

- Ошибка относится к действию, которое её вызвало, и отображается рядом с соответствующей формой или областью.
- Сообщение пользователю не содержит токен, полный URL запроса или сырой ответ с чувствительными данными.
- Ошибка входа или проверки номера требует явного повторного действия пользователя.
- Ошибка отправки сохраняет черновик.
- Временная ошибка polling не блокирует ввод и отправку сообщений.
- После временной ошибки polling повторяется с задержками `1`, `2`, `5`, затем не более `10` секунд между попытками.
- После успешного ответа задержка сбрасывается.
- При ошибке авторизации или доступа polling останавливается до повторного входа.

## 11. Интерфейс и адаптивность

### 11.1. Общие требования

- Визуальная основа — предоставленная в проекте вёрстка по мотивам MAX.
- Текст интерфейса должен однозначно сообщать, что сообщения отправляются через WhatsApp и GREEN-API.
- Стили оформляются CSS Modules.
- Цвета, размеры, тени, радиусы и другие переиспользуемые значения задаются дизайн-токенами.
- Все интерактивные элементы имеют видимые состояния `hover`, `focus`, `disabled` и, где применимо, `loading`.

### 11.2. Desktop

При ширине viewport от `768px` одновременно отображаются:

- боковая панель с брендом, текущим чатом и кнопкой «Новый чат»;
- область текущей переписки или пустое состояние до создания чата.

Форма создания чата может открываться как диалог или отдельное состояние боковой панели, не разрушая текущий чат до успешной проверки номера.

### 11.3. Mobile

При ширине viewport менее `768px` используются отдельные представления:

1. Экран выбора и создания чата.
2. Полноэкранная переписка.

В переписке присутствует кнопка возврата на экран чата. Возврат не удаляет историю и не останавливает получение сообщений. Создание успешно проверенного нового чата заменяет текущий.

Интерфейс не должен создавать горизонтальную прокрутку на поддерживаемой ширине от `320px`.

## 12. Доступность

- Каждое поле имеет связанный `label`.
- Все сценарии доступны с клавиатуры.
- Формы отправляются клавишей Enter.
- Фокус имеет видимый индикатор.
- Ошибки и изменения асинхронного состояния объявляются через `aria-live`.
- Кнопки только с иконкой имеют доступное имя.
- Диалог создания чата, если он используется, управляет фокусом и закрывается клавишей Escape.
- Цвет не является единственным способом передачи состояния.

## 13. Хранение и безопасность

- Реквизиты, активный чат и сообщения хранятся только в памяти приложения.
- Перезагрузка страницы полностью очищает сессию.
- `localStorage`, `sessionStorage`, IndexedDB и cookies для этих данных не используются.
- `apiTokenInstance` отображается как пароль и не выводится в логах или ошибках.
- `.env.development.local` допускается только для локальной разработки и не включается в Git.
- Переменные с префиксом `VITE_` считаются публичными для клиентского кода и не используются как защищённое хранилище production-секретов.
- Production-сборка не должна содержать тестовые реквизиты.
- Приложение не подключает сторонние скрипты без необходимости.

Frontend-only архитектура не скрывает токен от пользователя браузера и не предназначена для общего доступа недоверенных пользователей к одному инстансу.

## 14. Требования к тестированию

### 14.1. Автоматические тесты

Необходимо проверить:

- нормализацию и валидацию номера;
- формирование URL и тела каждого используемого метода;
- отсутствие токена в создаваемых пользовательских ошибках;
- успешный и ошибочный вход;
- обработку всех значимых состояний инстанса;
- успешную и ошибочную проверку номера;
- замену активного чата;
- успешную отправку и сохранение черновика при ошибке;
- обработку входящего текстового сообщения;
- фильтрацию другого чата и неподдерживаемого события;
- дедупликацию по `idMessage`;
- последовательность `ReceiveNotification → обработка → DeleteNotification`;
- повторные попытки и остановку polling;
- очистку сессии после размонтирования.

Для компонентных тестов используются моки API и управляемые таймеры. Автоматические тесты не обращаются к реальному GREEN-API.

### 14.2. Ручная проверка

Необходимо проверить:

- полный сценарий с реальным авторизованным инстансом;
- получение ответа, отправленного из WhatsApp;
- замену чата;
- поведение при неверных реквизитах и несуществующем номере;
- desktop layout;
- mobile layout на ширине `320px` и типовом мобильном viewport;
- управление формами только клавиатурой;
- отсутствие реальных реквизитов в Git и production-сборке.

## 15. Критерии приёмки

### AC-01. Вход

При корректных реквизитах авторизованного инстанса пользователь переходит к экрану чата. При ошибочных реквизитах или состоянии, отличном от `authorized`, переход не выполняется и показано понятное сообщение.

### AC-02. Создание чата

Корректный номер с WhatsApp создаёт активный чат. Некорректный номер или `existsWhatsapp: false` не заменяет текущий чат и сопровождается сообщением об ошибке.

### AC-03. Замена чата

После успешной проверки нового номера старый чат и его локальная история удаляются, а polling продолжает работу только для нового активного чата.

### AC-04. Отправка

Непустое текстовое сообщение отправляется в активный чат и появляется в истории после успешного ответа API. При ошибке черновик сохраняется, а дубликат сообщения не создаётся.

### AC-05. Получение

Входящее текстовое сообщение активного чата появляется в интерфейсе без ручного обновления страницы. Повторное получение одного `idMessage` не создаёт дубликат.

### AC-06. Очередь

Каждое полученное уведомление обрабатывается последовательно и подтверждается через `DeleteNotification`. Ошибка удаления не запускает параллельное чтение следующего элемента очереди.

### AC-07. Сессия

Реквизиты, чат и сообщения отсутствуют после перезагрузки страницы. В постоянных браузерных хранилищах данные не появляются.

### AC-08. Адаптивность

Основной сценарий выполняется на desktop и при ширине от `320px`. На мобильном экране пользователь может создать чат, открыть переписку, отправить сообщение и вернуться назад без потери текущей истории.

### AC-09. Доступность

Основной сценарий выполняется с клавиатуры, фокус виден, поля имеют подписи, а ошибки доступны assistive technologies.

### AC-10. Качество

Проект собирается без ошибок TypeScript, автоматические тесты проходят, а репозиторий не содержит реальных реквизитов GREEN-API.

## 16. Поддерживаемое окружение

- актуальные стабильные версии Chrome, Firefox, Safari и Edge;
- мобильные Chrome и Safari;
- JavaScript и Fetch API доступны;
- браузер разрешает запросы к GREEN-API в соответствии с политикой CORS поставщика.

Если GREEN-API перестаёт разрешать прямые запросы с origin приложения, это считается внешним ограничением frontend-only архитектуры, а не исправимой на клиенте ошибкой.
