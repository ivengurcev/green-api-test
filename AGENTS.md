# Правила работы с репозиторием

## Контекст и источники требований

Это фронтовое тестовое задание: React-клиент отправляет и получает текстовые сообщения WhatsApp через GREEN-API напрямую из браузера.

Перед изменениями прочитайте:

1. `README.md` — исходные требования и запуск.
2. `docs/mvp-requirements.md` — основной источник продуктовых и технических требований MVP.
3. `docs/frontend-only-architecture.md` — обоснование frontend-only решения и принятые риски.

Если документы расходятся, приоритет имеет `docs/mvp-requirements.md`. Не расширяйте MVP функциями из раздела «Не входит в MVP» без прямого запроса пользователя.

Общайтесь с пользователем и ведите документацию на русском языке. Идентификаторы, типы, команды и названия API оставляйте в исходном виде.

## Архитектурные ограничения

- Приложение остаётся frontend-only. Не добавляйте backend, proxy, BFF или серверное хранение.
- GREEN-API вызывается через небольшой типизированный REST-клиент на `fetch`. Не вызывайте `fetch` из React-компонентов и не подключайте SDK без отдельного согласования.
- Используйте `https://api.green-api.com` и только методы, перечисленные в ТЗ.
- Поддерживается один активный чат. Новый успешно проверенный чат заменяет предыдущий вместе с локальной историей.
- Данные существуют только в памяти вкладки. Не используйте `localStorage`, `sessionStorage`, IndexedDB или cookies.
- Получайте уведомления одним последовательным циклом `ReceiveNotification → обработка → DeleteNotification`. Не запускайте параллельные consumers.
- Останавливайте и отменяйте polling при замене чата и размонтировании. Дедуплицируйте входящие сообщения по `idMessage`.
- Отображайте только `textMessage` и `extendedTextMessage`; остальные уведомления подтверждайте без отображения.

## Безопасность реквизитов

- Никогда не добавляйте реальные `idInstance` и `apiTokenInstance` в Git, тесты, документацию, логи или тексты ошибок.
- Считайте любые `VITE_*` значения доступными клиентскому коду. `.env.development.local` предназначен только для локального удобства.
- Не включайте токен или полный URL запроса в пользовательские ошибки.
- Не меняйте правила хранения реквизитов без явного изменения ТЗ.

## UI и стили

- Сохраняйте визуальное направление существующего макета по мотивам MAX, но в текстах однозначно называйте WhatsApp и GREEN-API.
- Используйте CSS Modules для компонентных стилей и `src/client/styles/tokens.css` для общих дизайн-токенов.
- Поддерживайте desktop layout от `768px` и mobile layout от `320px` без горизонтальной прокрутки.
- Все формы должны работать с клавиатуры; поля имеют `label`, иконки-кнопки — доступное имя, ошибки и асинхронные статусы — `aria-live`.

## Разработка и тестирование

- Для продуктовых изменений используйте TDD: сначала наблюдаемый падающий тест, затем минимальная реализация и повторная проверка.
- Тестируйте поведение пользователя и публичные интерфейсы, а не внутренние детали React-компонентов.
- Сетевые тесты используют mock `fetch` или mock API-клиента и никогда не обращаются к реальному GREEN-API.
- Для polling используйте управляемые таймеры и проверяйте последовательность вызовов, отмену, backoff и дедупликацию.
- Сохраняйте строгую типизацию; не используйте `any` для обхода контрактов внешнего API. Неизвестные ответы сначала считайте `unknown` и проверяйте перед использованием.
- Делайте небольшие целевые изменения и сохраняйте посторонние пользовательские правки.

Перед завершением запускайте актуальные команды из `package.json`; минимально необходимы тесты, проверка TypeScript и production-сборка. Затем проверьте `git diff --check` и `git status --short`.

## Документация

При изменении поведения синхронизируйте `README.md`, ТЗ и архитектурное решение. Ссылки на GREEN-API должны вести на официальную документацию. Известные ограничения прямой браузерной интеграции не скрывайте и не описывайте как production-безопасную архитектуру.
